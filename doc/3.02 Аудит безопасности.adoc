=== Аудит безопасности

Документ описывает механизмы логирования событий безопасности и ключевые метрики для мониторинга аномального поведения. Связь с FR-003 (логирование попыток доступа и отказанных запросов), FR-004 (логирование), NFR-005 (аудит безопасности), 2.06 (схема audit_logs, security_events), 2.09 (Observability), 2.10 (реагирование на инциденты).

==== Логирование событий безопасности

*Цель:* фиксировать все значимые события, связанные с аутентификацией, авторизацией и доступом к конфиденциальным данным, для расследования инцидентов, соответствия (SOC 2, GDPR) и обнаружения аномалий.

===== Какие события логировать

*Аутентификация:*

  * *Успешный вход (LOGIN_SUCCESS):* пользователь успешно аутентифицирован (OAuth2/OIDC, обмен code на токены). Поля: user_id (или subject из JWT), ip_address, user_agent, timestamp, client_id (если применимо). Событие публикуется при успешном логине (API Gateway или отдельный endpoint, вызываемый после обмена токена в IAM).
  * *Неуспешный вход (LOGIN_FAILURE):* неверные учётные данные, отозванный или истёкший refresh token, ошибка IAM. Поля: ip_address, user_agent, reason (invalid_credentials, token_expired, account_locked и т.д.), timestamp; user_id — только если удалось определить (например, по email в запросе, без логирования самого пароля). Источник: API Gateway или сервис, обрабатывающий логин.
  * *Выход (LOGOUT):* явный logout пользователя, отзыв refresh token. Поля: user_id, session_id, ip_address, timestamp.
  * *Истечение сессии / таймаут неактивности:* при необходимости — событие или учёт в логах (низкий приоритет по объёму).

*Авторизация и доступ к API:*

  * *Отказ в доступе (UNAUTHORIZED_ACCESS / 401, 403):* запрос без валидного токена (401) или с недостаточными правами (403). Поля: request_id, method, path (endpoint), user_id (если токен был передан и валиден), ip_address, user_agent, status_code (401/403), reason (missing_token, invalid_token, insufficient_permissions, forbidden_resource), timestamp. Источник: API Gateway — на каждый ответ 401/403 генерировать событие и публиковать в топик audit/security для Audit Service.
  * *Доступ к конфиденциальным данным и критичным операциям:* успешные вызовы к чувствительным ресурсам логируются в audit_logs (2.06) для трассировки «кто что посмотрел/изменил». К числу чувствительных относятся: просмотр/изменение профиля (users), операции с платежами (payments), назначение/снятие ролей (admin/users/roles), экспорт данных, доступ к аудит-логам. Поля: user_id, session_id, service_name, action (READ/UPDATE/EXECUTE и т.д.), resource_type, resource_id, request_id, ip_address, status_code, created_at; тело запроса/ответа — не логировать или только метаданные (3.03, маскирование PII). Источник: микросервисы при обработке запроса публикуют событие в Event Bus (audit.events), Audit Service потребляет и пишет в audit_logs.

*Изменения прав и учётных записей:*

  * *Назначение/снятие роли (ROLE_GRANTED, ROLE_REVOKED):* кто, кому, какую роль, когда (3.01). Поля: actor_user_id, target_user_id, role_name, action (grant/revoke), timestamp. Источник: User Service при вызове админ-API; событие в Kafka → Audit Service → audit_logs и при необходимости security_events с severity HIGH для роли ADMIN.
  * *Смена пароля, сброс пароля, блокировка учётной записи:* при наличии соответствующих операций — события с user_id, ip_address, timestamp; пароли и токены не логировать.

*Доступ к секретам (Vault):*

  * Обращения к Vault (чтение секретов, обновление) логируются самим Vault (3.04). Рекомендуется пересылать аудит-лог Vault в централизованное хранилище (Elasticsearch/Loki) и при необходимости в топик security для корреляции с событиями приложений. События доступа к секретам можно учитывать в метриках аномалий (необычно частый доступ к одному path).

*Ошибки и сбои безопасности:*

  * *Подозрительная активность (SUSPICIOUS_ACTIVITY):* ручное или автоматическое создание события при выявлении паттерна (например, множество 403 с одного IP, попытки доступа к чужим ресурсам по подбору ID). Поля: event_type, severity (MEDIUM/HIGH/CRITICAL), description, ip_address, user_id (если есть), metadata, timestamp. Запись в security_events.

*Формат и поток событий:*

  * События публикуются в Kafka в топики `audit.events` (операции над ресурсами, audit_logs) и при необходимости отдельный топик `security.events` (события аутентификации и авторизации для security_events). Формат сообщения — JSON с полями, перечисленными выше; обязательные: event_type (или action), timestamp, request_id (если есть); без паролей, токенов и чувствительных полей в открытом виде (3.03).
  * Audit Service подписан на топики, парсит сообщения, обогащает при необходимости и пишет в PostgreSQL: audit_logs — для операций доступа к ресурсам; security_events — для LOGIN_*, UNAUTHORIZED_ACCESS, ROLE_*, SUSPICIOUS_ACTIVITY. Схема таблиц — 2.06 (audit_logs: service_name, action, resource_type, resource_id, status_code, user_id, ip_address, …; security_events: event_type, severity, user_id, ip_address, description, metadata, created_at).
  * Дублирование в общий лог (Fluent Bit → Kafka → Elasticsearch): при необходимости события безопасности попадают и в общий лог-индекс для поиска в одном месте; маскирование PII по правилам 3.03.

===== Где генерировать события

[options="header",cols="1,1,2"]
|===
| Компонент
| События
| Куда

| API Gateway
| 401, 403, успешный логин (если логин через Gateway), 429 (rate limit)
| Публикация в Kafka (audit.events / security.events) или отправка в Audit Service по HTTP; при высокой нагрузке — асинхронно через Kafka

| User Service
| Назначение/снятие ролей, смена пароля (если в зоне ответственности), доступ к профилю (audit)
| Event Bus (audit.events) → Audit Service → audit_logs, security_events

| Payment Service, Request Processing Service, Notification Service
| Успешные/неуспешные операции над платёжными данными, запросами, уведомлениями (audit)
| Event Bus (audit.events) → Audit Service → audit_logs

| IAM (Keycloak)
| События входа/неудачи (при наличии Event Listener или экспорта в SIEM); при отсутствии — дублирование из Gateway
| Передача в Kafka/логи или опора на события от Gateway

| Audit Service
| Запись в audit_logs, security_events; при обнаружении паттерна — создание SUSPICIOUS_ACTIVITY
| PostgreSQL (audit_db)
|===

==== Ключевые метрики для мониторинга аномального поведения

Метрики предназначены для дашбордов и алертов (2.09, 2.10); сбор — Prometheus/OpenTelemetry из приложений и из логов (например, экспорт счётчиков из Audit Service или лог-агрегатора).

*Аутентификация:*

  * *Количество неуспешных попыток входа в единицу времени* (по всему кластеру и в разбивке по ip_address, user_id/identifier). Алерт: рост выше порога (например, > 50 за 5 мин по одному IP или > 2% от успешных за 10 мин без всплеска легитимного трафика) — возможный brute-force (2.10).
  * *Соотношение успешных и неуспешных логинов* (rate login_success, rate login_failure). Резкое увеличение доли неуспешных — признак атаки или сбоя IAM.
  * *Количество запросов с 401 (Missing/Invalid token)* по endpoint и по IP. Массовый 401 с одного IP — сканирование или неверная настройка клиента.

*Авторизация:*

  * *Количество ответов 403 (Forbidden) в единицу времени* — по user_id, по ip_address, по endpoint (path). Алерт: аномальный рост 403 по одному пользователю или по одному IP (перебор чужих ресурсов, эскалация привилегий).
  * *Доступ к чувствительным endpoint'ам:* rate запросов к /api/v1/admin/*, /api/v1/users/*/roles, /api/v1/payments/* по user_id и по роли. Необычно высокий доступ с роли USER к админ-путям (при корректной проверке прав таких запросов быть не должно — метрика для верификации и расследований).

*Rate limiting и злоупотребления:*

  * *Количество ответов 429 (Too Many Requests)* по user_id, по IP, по endpoint. Алерт при аномальном росте 429 (2.09), в частности на endpoint логина — защита от brute-force.
  * *Топ IP и user_id по количеству отказов (403 + 429 + login_failure)* за скользящее окно (например 1 ч). Использование для ручного ревью и блокировок.

*События безопасности (security_events):*

  * *Количество событий по event_type и severity* за период (например за час): LOGIN_FAILURE, UNAUTHORIZED_ACCESS, SUSPICIOUS_ACTIVITY, CRITICAL severity. Алерт при превышении порога по CRITICAL или по резкому росту UNAUTHORIZED_ACCESS.
  * *Количество назначений роли ADMIN (ROLE_GRANTED для ADMIN)* за период. Редкое событие; алерт при каждом таком событии или при нескольких за короткий интервал — ревью по 3.01.

*Доступ к данным и аудит:*

  * *Количество записей в audit_logs по action и resource_type* (READ/UPDATE по payments, users и т.д.). Помогает выявить аномальный объём чтения конфиденциальных данных (например, массовый экспорт).
  * *Задержка записи в audit_db (lag потребителя Kafka)*. Рост lag — риск потери событий при сбое; алерт по 2.09/2.10.

*Сводная таблица метрик и алертов:*

[options="header",cols="2,2,2"]
|===
| Метрика
| Назначение
| Порог алерта (пример)

| login_failure_rate (по IP, глобально)
| Brute-force, компрометация учётных записей
| > 50 за 5 мин по IP или > 2% за 10 мин глобально

| http_403_total (по user_id, по path)
| Перебор прав, доступ к чужим ресурсам
| Резкий рост по одному user_id или по чувствительному path

| http_429_total (по endpoint)
| Злоупотребление, brute-force на логин
| Аномальный рост, особенно на /auth/login

| security_events_total (severity=CRITICAL)
| Критичные инциденты
| > 0 за 5 мин или рост по сравнению с базой

| audit_logs_write_lag (Kafka consumer)
| Потеря событий аудита
| Lag > N сообщений или > M минут
|===

==== Интеграция с Observability и реагированием

  * *Дашборды:* в Grafana (2.09) выделить дашборд «Безопасность и аудит»: метрики аутентификации (успех/неудача), 401/403/429 по endpoint и по источнику, счётчики security_events по типу и severity, топ IP/user по отказам. При необходимости — ссылки на запросы в логах (request_id) для расследования.
  * *Алерты и runbook:* алерты по перечисленным метрикам направляются в Alertmanager / Grafana Alerting с маршрутизацией в канал «Безопасность» (Slack, PagerDuty); в 2.10 зафиксировать runbook по «Рост отказов аутентификации» и при необходимости добавить runbook «Аномальный рост 403» и «Критичные security_events».
  * *Ретенция и расследование:* аудит-логи и security_events хранятся в audit_db с партиционированием по дате (2.13); hot retention 30–90 дней для быстрого поиска; экспорт в Elasticsearch для полнотекстового поиска при расследованиях; маскирование PII при экспорте (3.03, роль AUDITOR в 3.01).

*Итог:* механизмы логирования событий безопасности охватывают аутентификацию (успех/неудача, logout), ошибки авторизации (401, 403), доступ к конфиденциальным данным и критичным операциям (audit_logs), изменение ролей и подозрительную активность (security_events). События публикуются в Kafka и обрабатываются Audit Service с записью в audit_db. Ключевые метрики для аномалий — rate неуспешных логинов, 403 и 429 по пользователю/IP/endpoint, счётчики security_events по типу и severity, назначения роли ADMIN; алерты и дашборды интегрированы с Observability и планом реагирования (2.09, 2.10).
