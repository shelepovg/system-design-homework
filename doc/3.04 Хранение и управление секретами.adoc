=== Хранение и управление секретами

Документ описывает выбор инструмента для управления секретами, схему хранения ключей, паролей, токенов и конфигураций, процесс ротации секретов и шифрование конфигурационных данных. Исходные требования: NFR-005 (хранение в защищённом хранилище, ротация, минимальные права, аудит доступа к секретам); связь с 2.13 (KMS, шифрование в покое) и 3.03 (ключи для field-level шифрования).

==== Выбор инструмента: HashiCorp Vault

*Решение:* использовать **HashiCorp Vault** как единую систему управления секретами и криптографическими ключами.

*Обоснование:*

  * *Единая точка хранения:* пароли БД, Redis, Kafka, API-ключи внешних систем (платежи, уведомления), client_secret для IAM, webhook-секреты, ключи шифрования (для field-level и конфигураций) хранятся в Vault; приложения не хранят секреты в коде и по возможности не в переменных окружения на диске.
  * *Движки (engines):* KV v2 — статические секреты (API keys, webhook secret); Database — динамические учётные записи для PostgreSQL (краткосрочные логины с автоматической ротацией); Transit — шифрование/расшифрование данных без выдачи ключа приложению (для конфигураций и field-level при интеграции с Vault).
  * *Аутентификация приложений:* AppRole или Kubernetes Auth Method — каждый сервис (или под) получает ограниченный токен с доступом только к своим путям в Vault; принцип наименьших привилегий (NFR-005).
  * *Аудит:* Vault логирует все обращения к секретам (чтение, обновление, создание); аудит-лог можно пересылать в централизованное хранилище (2.09, 3.02).
  * *Интеграция со стеком:* Spring Boot (Vault Spring Cloud Vault или Vault Java API), Keycloak, CI/CD — получение секретов при старте приложения или при деплое; при развёртывании в Kubernetes — Vault Agent (sidecar или init) для записи секретов в файлы/переменные окружения.

Альтернативы (AWS Secrets Manager, Azure Key Vault, корпоративный Vault) допустимы при размещении в соответствующем облаке; схема ниже ориентирована на Vault и при необходимости переносима на другой KMS/секрет-менеджер с аналогичными возможностями (KV, dynamic credentials, audit).

==== Схема безопасного хранения секретов в Vault

*Структура путей (namespace/path):* использование одного Vault namespace на окружение (например, `prod`, `staging`) и иерархии путей по сервисам и типу секрета снижает риск ошибочного доступа и упрощает политики.

*Какие секреты хранятся и где (логическая схема):*

|===
| Категория

*Движки Vault:*

  * *KV Secrets Engine v2:* статические секреты (пароли Redis, Kafka, API keys, webhook secret). Версионирование позволяет откатиться при ошибке; политики Vault ограничивают доступ по path.
  * *Database Secrets Engine:* для PostgreSQL — Vault генерирует краткосрочные учётные записи (TTL, например 1 час) и при необходимости автоматически ротирует их. Сервисы запрашивают новый логин/пароль при старте или по истечении TTL; статические пароли в БД не требуются для приложений.
  * *Transit Secrets Engine:* шифрование/расшифрование данных без выдачи ключа: приложение отправляет plaintext/ciphertext в Vault, получает результат. Подходит для шифрования конфигурационных значений и при необходимости для field-level без извлечения DEK в приложение (NFR-005, 2.13).
  * *PKI (опционально):* выпуск и хранение сертификатов для внутренних сервисов или edge; ротация через Vault.

*Политики доступа (ACL):* для каждого сервиса (AppRole) задаётся минимальный набор путей: только те секреты, которые нужны этому сервису. Пример: Payment Service — только `secret/prod/payment`, `database/creds/payments-db`, при необходимости `secret/prod/kafka`. Отказ по умолчанию для всех остальных путей.

==== Процесс ротации секретов

*Динамические секреты (PostgreSQL через Database engine):*

  * Vault сам генерирует учётные записи с ограниченным TTL (например 1 час). По истечении TTL учётная запись аннулируется в БД (Vault отзывает пользователя).
  * Ротация «встроена»: приложение при следующем запросе к Vault получает новые credentials. Дополнительный процесс ручной ротации не нужен для этих логинов.
  * Ротация статических учётных записей *в самой БД* (например, мастер-пользователь, которым Vault создаёт динамических пользователей): по регламенту (например раз в 90 дней); обновление credentials в Vault Database config и при необходимости перевыпуск динамических токенов.

*Статические секреты (API keys, webhook secret, Redis, Kafka, IAM client_secret):*

  * *Периодичность:* не реже чем раз в 90 дней (NFR-005); для высокорисковых (платёжный API key, webhook secret) — по регламенту провайдера или чаще.
  * *Шаги ротации:*
    1. Создание нового секрета (новый API key у провайдера, новый пароль Redis/Kafka и т.д.).
    2. Запись новой версии в Vault (KV v2) по тому же path; при необходимости две версии (старая и новая) для плавного переключения.
    3. Обновление конфигурации потребителя: перезапуск сервисов или обновление через Vault Agent / перечитывание при следующем TTL. Для внешних систем (webhook) — обновление секрета у провайдера после переключения всех инстансов на новый секрет.
    4. Удаление или деактивация старой версии секрета после перехода.
  * *Автоматизация:* где возможно — скрипты или CI/CD job, которые по расписанию (cron) или по событию генерируют новый секрет, записывают в Vault и триггерят перезапуск/обновление потребителей (с ограничениями: платёжный провайдер может требовать ручного выпуска нового key). Аудит: все операции записи в Vault логируются (3.02).

*Ротация ключей шифрования (Transit / KEK в Vault):*

  * В соответствии с 2.13 и NFR-005 — ротация мастер-ключей каждые 90 дней. В Transit можно создать новую версию ключа (key versioning); старые данные расшифровываются старой версией, новые — новой; перешифрование данных — по политике (постепенно при доступе или отдельным job).
  * Для ключей в KV (если DEK хранятся там): ротация — создание нового DEK, перешифрование данных новым DEK (фоново или при записи), затем удаление старого DEK из активного использования.

==== Шифрование конфигурационных данных

*Проблема:* конфигурации (application.yml, env, конфиг-сервер) могут содержать чувствительные значения (connection strings, пароли, API keys). Хранение их в открытом виде в репозитории или на диске инстанса повышает риск утечки.

*Подходы:*

  * *Секреты только в Vault, не в конфиге:* все чувствительные значения приложение получает из Vault при старте (Spring Cloud Vault, Vault Agent). Конфигурационные файлы в репозитории содержат только несекретные параметры и путь к Vault (адрес, роль для AppRole/K8s auth). Секреты на диск не записываются или записываются во временный файл с ограниченными правами и удаляются после чтения.
  * *Шифрование конфигов в репозитории (опционально):* если часть конфигурации должна храниться в Git (например, шаблоны), чувствительные поля шифруются до коммита (например, SOPS с ключом, хранящимся в Vault или в облачном KMS). При деплое расшифровка выполняется в CI/CD или на узле с доступом к ключу; результат передаётся приложению через переменные окружения или файл, не попадающий в репозиторий.
  * *Transit для шифрования значений:* конфигурация может содержать зашифрованные строки (ciphertext); при старте приложение отправляет их в Vault Transit для расшифровки и использует plaintext в памяти. Ключ шифрования не покидает Vault.

*Рекомендация для системы:* основной способ — *все секреты в Vault*, приложение подключается к Vault по AppRole или Kubernetes Auth и подтягивает секреты при старте; конфигурационные файлы и переменные окружения без секретов. Ротация секретов выполняется в Vault без изменения кода; при необходимости перезапуск сервисов или обновление через Vault Agent для подхвата новой версии.

==== Связь с компонентами решения

  * *Микросервисы (User Service, Request Processing Service, Payment Service, Notification Service, Audit Service):* получают из Vault учётные данные БД (dynamic или static), Redis, Kafka, при необходимости — API keys внешних систем (Payment Service — платёжный API и webhook secret; Notification Service — ключи провайдера уведомлений). Конфигурация без секретов; секреты инжектируются при старте.
  * *API Gateway:* из Vault — client_id/client_secret для Keycloak (если нужны server-side вызовы к IAM), при необходимости конфигурация rate limit или другие параметры.
  * *IAM (Keycloak):* пароли пользователей и внутренние секреты Keycloak могут оставаться в Keycloak; для интеграции с Vault (например, синхронизация учётных записей или хранение master-пароля Keycloak в Vault) — отдельная настройка. Сервисы не хранят пароли пользователей; они хранятся в Keycloak (3.01).
  * *KMS для шифрования в покое (2.13):* Vault Transit или Vault как источник KEK/DEK для шифрования данных в PostgreSQL, Redis и бэкапах; альтернативно — облачный KMS (AWS KMS и т.д.), а в Vault — только прикладные секреты (пароли, API keys). В обоих вариантах ключи не лежат в коде и не в открытых конфигах.
