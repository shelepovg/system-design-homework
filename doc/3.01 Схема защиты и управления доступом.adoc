==== Выбор механизма аутентификации и авторизации

*Рекомендация:* использовать связку **OAuth 2.0 + OpenID Connect (OIDC) + JWT** для сценария системы, обслуживающей API и веб-/мобильные клиенты.

*Обоснование:*

* *OAuth 2.0 + OIDC* — стандарт для веб- и мобильных клиентов: Authorization Code Flow для интерактивного входа, возможность единого входа (SSO), делегирование авторизации без передачи пароля приложению.
* *JWT* — самодостаточные токены с подписью (RS256/ES256): проверка на стороне API Gateway по JWKS без обращения к IAM на каждый запрос; роли и разрешения в claims ускоряют авторизацию.
* *SAML* не выбирается для данного сценария: ориентирован на enterprise SSO через браузер (redirects, XML), избыточен для мобильных и API-first сценариев; OIDC проще для интеграции с SPA и нативными приложениями.

В модели это отражено: внутренняя подсистема *IAM (Keycloak)* выдаёт и хранит учётные данные; *API Gateway* валидирует JWT и проверяет права; при необходимости используется внешний *iam_ext* (OAuth2) для логина и refresh. Связи api-gateway → iam (валидация JWT, JWKS) и api-gateway → iam_ext (логин, refresh) покрывают оба сценария.

==== Выдача и проверка токенов доступа

*Выдача токенов:*

* *Веб-клиент (SPA):* Authorization Code Flow с PKCE. Пользователь перенаправляется на IAM (Keycloak); после успешной аутентификации IAM возвращает `code` в redirect_uri; Frontend (через API Gateway или напрямую к IAM) обменивает `code` + `code_verifier` на пару access_token (JWT) + refresh_token. Пароль не передаётся во Frontend.
* *Мобильные клиенты (Android/iOS):* тот же Authorization Code Flow с PKCE либо использование нативных SDK Keycloak; токены хранятся в secure storage (Keychain/Keystore).
* *Сервис-сервис (Backend → внешние системы или внутренние вызовы с идентичностью сервиса):* Client Credentials Flow — сервис получает JWT по client_id/client_secret для машинной аутентификации.

Выдача выполняется в IAM (Keycloak); в модели это соответствует связям: клиенты → load-balancer → front → api-gateway, далее api-gateway → iam_ext (логин/обмен кода на токены). User Service синхронизирует пользователей и сессии с Keycloak (user-service → iam).

*Проверка токенов:*

* *На каждом запросе к API:* клиент передаёт `Authorization: Bearer <access_token>`. API Gateway проверяет JWT: подпись по JWKS (ключи с HTTPS endpoint IAM), проверка `exp`, `iat`, `iss`, `aud`; при необходимости проверка отзыва (черный список в Redis или вызов introspect). После валидации Gateway извлекает `sub`, роли и при необходимости permissions, передаёт контекст (User-ID, роли) в Backend и выполняет маршрутизацию.
* *JWKS:* API Gateway кэширует JWKS от IAM и обновляет по TTL или при ошибке проверки подписи; это снижает нагрузку на IAM и задержку. В модели это отражено в связи api-gateway → iam «Валидация JWT, проверка прав, JWKS».

==== Кэш и JWT (FR-006, согласование TTL)

*Корректная модель (рекомендация):*

* *Проверка `exp`, `iss`, `aud` и извлечение ролей* выполняются **на каждом запросе** из **тела переданного клиентом JWT** (локально, после проверки подписи по ключам из кэшированного JWKS). Срок жизни access token **определяется только** полем `exp` в токене, а не TTL записи в Redis для «токена».
* В Redis (FR-006) кэшируют **не сам access JWT как замену валидации**, а: **JWKS** (открытые ключи; TTL может быть больше 30 мин), **профили/сессии пользователя** в User Service (отдельно от периметра Gateway), **чёрный список** отозванных `jti` / сессий — с TTL **не дольше** оставшегося времени жизни связанного access token (или фиксированно ≤ 15–30 мин в зависимости от политики).
* Если используется кэш ответов **introspection** — TTL записи **≤** времени, указанному IAM в ответе (и не дольше `exp` токена).

Таким образом, выдача централизована в IAM, проверка — на периметре в API Gateway с опорой на JWT и JWKS, без обязательного вызова IAM на каждый запрос.

==== Схема процессов аутентификации и авторизации

Ниже — упрощённая схема потоков: первичный вход (логин), проверка доступа при запросе к API и обновление токена. Пометки *sync* и *async* соответствуют модели LikeC4; события 401/403 и логина публикуются в Event Bus для Audit Service (3.02).

[source,text]
----
Client (Web / Android / iOS)
   │
   ├──sync──► Load Balancer
   │              │
   │              └──sync──► API Gateway
   │                             │
   │                             ├── [Логин] sync──► IAM внешний (Authorization Code + PKCE)
   │                             │              │    redirect на IAM → ввод учётных данных → redirect с code
   │                             │              │    обмен code + code_verifier → access_token (JWT) + refresh_token
   │                             │              ├──sync──► Frontend: передача токенов в secure storage
   │                             │              └──async──► Event Bus (security.events): LOGIN_SUCCESS / LOGIN_FAILURE
   │                             │
   │                             ├── [Запрос с JWT] проверка Authorization: Bearer <token>
   │                             │              ├──sync──► JWKS из кэша (Redis) на Gateway или IAM: подпись JWT; exp/iss/aud — всегда по claims токена на каждом запросе; извлечение sub, ролей
   │                             │              │    при успехе:
   │                             │              ├──sync──► User Service / Request Processing / Payment / Notification (с контекстом user_id, роли; RBAC)
   │                             │              │    при 401 или 403:
   │                             │              └──async──► Event Bus (security.events): UNAUTHORIZED_ACCESS → Audit Service
   │                             │
   │                             ├── [Refresh токена] sync──► IAM внешний (grant_type=refresh_token)
   │                             │              │    при успехе: новая пара access_token + refresh_token → клиент
   │                             │              └── при неуспехе: 401 → клиент перенаправляется на логин
   │                             │
   │                             └── sync──► IAM (Keycloak): JWKS для проверки подписи JWT; кэш JWKS на Gateway
   │
   User Service ──sync──► IAM (синхронизация пользователей, сессий, ролей; при назначении/снятии роли — публикация в audit.events)
   User Service ──sync──► Redis (кэш профилей, сессий; при отзыве токена — чёрный список или флаг сессии)
----

*Примечание.* Логин для SPA/мобильных идёт через IAM внешний (OAuth2/OIDC); при использовании внутреннего Keycloak без внешнего IdP связь «API Gateway → IAM внешний» заменяется на «API Gateway → IAM (Keycloak)». Проверка прав (RBAC) выполняется на API Gateway по ролям из JWT и при необходимости детально в сервисе (проверка владельца ресурса).

==== Архитектура экспирации и обновления токенов

*Сроки жизни (согласовано с FR-002 и эталоном Keycloak `keycloak/realm-system-design.json`):*

* *Access token (JWT):* в импортируемом realm — *15 минут* (900 с, `accessTokenLifespan`); в требованиях FR-002 допускается диапазон *15–30 минут* при настройке другого значения. Короткий срок снижает риски при утечке; проверка на каждом запросе по подписи и `exp`.
* *SSO-сессия Keycloak (границы refresh):* обновление access по `refresh_token` возможно *пока действует SSO-сессия* в Keycloak, а не произвольные «7–30 дней» срока refresh как отдельной сущности. В эталонной конфигурации:
  ** *Неактивность:* `ssoSessionIdleTimeout` = 30 мин (1800 с) — при отсутствии активности сессия завершается (согласовано с FR-002).
  ** *Максимум сессии:* `ssoSessionMaxLifespan` = *24 часа* (86400 с) — с момента входа пользователь не может продлевать сессию через refresh дольше этого порога; затем требуется повторный логин.
* *Refresh token:* хранится на клиенте в secure storage (httpOnly cookie для SPA или secure storage для мобильных); не передаётся в каждом запросе, только при обновлении access. Включены rotation и отзыв (`refreshTokenMaxReuse`, `revokeRefreshToken` в realm). Долгоживущие *offline*-сессии (до 30 суток `offlineSessionIdleTimeout` в realm) — опционально для отдельных клиентов при scope `offline_access`, не заменяют ограничение интерактивной SSO 24 ч без явной настройки.

*Сценарий обновления (refresh):*

* Клиент (Frontend/мобильное приложение) обнаруживает истечение или скорое истечение access token (по `exp` или по ответу 401 от API Gateway).
* Клиент отправляет запрос на токен-эндпоинт IAM (через API Gateway или напрямую к IAM): `grant_type=refresh_token`, `refresh_token=<refresh_token>`. Запрос идёт по HTTPS; для публичных клиентов (SPA) дополнительно привязка к клиенту и rate limiting.
* IAM проверяет refresh token (валидность, не отозван) и состояние SSO-сессии (в т.ч. не превышены `ssoSessionIdleTimeout` и `ssoSessionMaxLifespan`), при успехе выдаёт новую пару access_token + опционально новый refresh_token (rotation). Старый refresh token при использовании rotation считается использованным и не принимается повторно.
* Клиент сохраняет новые токены и повторяет исходный запрос с новым access token.

В модели: обновление выполняется через ту же связь api-gateway → iam_ext «Логин, refresh токенов, синхронизация пользователей». Отдельного компонента «Token Refresh Service» не требуется — эту роль выполняет IAM при запросах от Gateway/клиента.

*Экспирация и отзыв:*

* *Экспирация:* JWT не отзывается до истечения `exp`; сокращение срока жизни access token (15–30 мин) ограничивает окно риска. Сессии в Keycloak и синхронизация с User Service (user-service → iam) позволяют учитывать «активные сессии» и при необходимости завершать их (logout всех устройств).
* *Отзыв (revocation):* при logout клиент вызывает endpoint отзыва IAM (revoke refresh_token); access token остаётся валидным до `exp`, поэтому при высоких требованиях можно сократить TTL access token или ввести чёрный список отозванных access token в Redis с TTL ≈ времени жизни токена. Кэш сессий/профилей (user-service → cache) может использоваться для хранения идентификаторов отозванных токенов или флагов сессии при реализации централизованного logout.

*Таймаут неактивности:* по FR-002 — автоматическое завершение неактивных сессий (например, 30 минут). Реализуется в IAM (Keycloak) настройками сессии и/или в User Service при синхронизации сессий; при истечении сессии refresh token перестаёт приниматься, клиент перенаправляется на повторный логин.

==== Модель управления доступом: RBAC vs ABAC

*Рекомендация для системы:* **RBAC (Role-Based Access Control)** с проверкой владения ресурсом в бизнес-логике. ABAC (Attribute-Based Access Control) на текущем этапе не вводится.

*Краткое сравнение:*

* *RBAC:* решение «разрешить/запретить» принимается на основе *ролей* субъекта (пользователь или сервисная учётная запись) и привязанных к ролям *разрешений* (операция + тип ресурса). Эталон системы — *восемь* ролей (см. ниже): четыре базовые пользовательские (ADMIN, OPERATOR, USER, VIEWER) и четыре расширения (SERVICE, SUPPORT, AUDITOR, BILLING). Роль определяет, какие действия (READ, WRITE, DELETE, EXECUTE, MANAGE) допустимы. Реализация: роли в JWT, маппинг «роль → разрешения» в Gateway и/или User Service; проверка на периметре (Gateway) и при необходимости детальная проверка в сервисе.
* *ABAC:* решение принимается на основе *атрибутов* субъекта, ресурса, действия и окружения (время, IP, метаданные). Политика формулируется в виде правил: «разрешить, если resource.owner_id == subject.id И resource.department == subject.department И action == READ». Требует политик-движка, подстановки атрибутов на каждый запрос, хранения и актуализации атрибутов ресурсов.

*Почему для данной системы подходит RBAC:*

* *Фиксированный набор ролей и разрешений (FR-003):* восемь ролей эталона (ADMIN, OPERATOR, USER, VIEWER, SERVICE, SUPPORT, AUDITOR, BILLING) и разрешения READ, WRITE, DELETE, EXECUTE, MANAGE однозначно заданы в 1.01 (актуализированный FR-003) и в настоящем документе. Нет требований к политикам вида «разрешить в зависимости от атрибута ресурса (отдел, метка конфиденциальности, регион) или окружения (время суток, IP)».
* *«Доступ только к своим данным» (контекстные разрешения):* реализуется как *RBAC + проверка владельца* в бизнес-логике: пользователь с ролью USER имеет разрешение READ/WRITE на «свои» запросы, платежи, уведомления; при выполнении запроса сервис проверяет `resource.user_id == current_user_id` (или аналог). Отдельный политик-движок и атрибуты ресурса для этого не требуются.
* *Совместимость со стеком:* Keycloak (IAM) и JWT изначально ориентированы на роли и группы; маппинг ролей в claims и проверка по ролям на Gateway — стандартный сценарий. Таблицы `user_roles` и `user_permissions` в users_db (модель данных, DBML) уже поддерживают хранение ролей и детальных разрешений по пользователю.
* *Производительность и простота:* проверка по ролям из JWT и по кэшированным permissions не требует запроса атрибутов ресурса и вычисления политик на каждый вызов; детальная проверка «свой/чужой ресурс» выполняется в сервисе при обращении к данным (один раз в рамках запроса).

*Когда имеет смысл рассматривать ABAC (на перспективу):*

* Появление политик вида «доступ к ресурсу только если у ресурса атрибут X (например, classification=internal) и у пользователя атрибут Y (clearance_level ≥ X)».
* Мультитенантность с доступом по атрибутам тенанта (tenant_id, region, segment) и сложными правилами между тенантами.
* Регуляторные требования к доступу по времени, месту, устройству (атрибуты окружения).
* Рост числа ролей и правил до такой степени, что управление только через роли становится громоздким и логичнее описывать политики атрибутами.

*Итог:* для текущих требований (FR-003, роли, детальные разрешения, контекст «только свои данные») достаточно **RBAC с проверкой владения ресурсом в сервисах**. Модель в проекте (User Service, роли и permissions, API Gateway как точка проверки) этому соответствует. ABAC можно зарезервировать как возможное расширение при появлении политик, не сводимых к ролям и владельцу.

==== Управление доступами (RBAC): роли, процессы, автоматизация

===== Роли системы и уровни прав

Модель RBAC реализуется набором *ролей* (техническое имя в IAM и JWT — латиницей; отображаемое имя — для интерфейсов и документации) и закреплённым за каждой ролью набором *разрешений* (READ, WRITE, DELETE, EXECUTE, MANAGE) по типам ресурсов. Контекст «только свои данные» для ролей USER и VIEWER обеспечивается проверкой `resource.user_id == current_user_id` в бизнес-логике сервисов.

*Эталон ролей (восемь, FR-003 актуализированный + Keycloak):* одна таблица. Первые четыре строки — *исходный* минимум из FR-003 (пользователи); следующие четыре — *расширение* архитектуры (сервисные и специализированные роли).

[options="header",cols="2,2,1,4"]
|===
| Техническое имя (JWT, БД)
| Отображаемое имя
| Класс
| Уровень прав и область применения

| ADMIN
| Администратор
| FR-003 (базовая)
| Полный доступ: управление пользователями, ролями, запросами (в т.ч. чужими), платежами, уведомлениями, настройками системы; доступ к админ-функциям и мониторингу; MANAGE на всех ресурсах.

| OPERATOR
| Оператор
| FR-003 (базовая)
| Управление запросами (приоритеты, отмена, повтор; в т.ч. чужих при необходимости), просмотр очередей и метрик; READ/WRITE/EXECUTE на запросы и мониторинг; без управления пользователями и ролями.

| USER
| Пользователь
| FR-003 (базовая)
| Создание и управление *собственными* запросами, платежами, уведомлениями, профилем; READ/WRITE/EXECUTE только в рамках своих ресурсов (проверка владельца в сервисах).

| VIEWER
| Наблюдатель
| FR-003 (базовая)
| Только просмотр *собственных* данных (запросы, платежи, уведомления, профиль); READ; без создания и изменения.

| SERVICE
| Сервис
| Расширение
| Машинная учётная запись для сервис-сервис вызовов, входящих webhook и фоновых задач. Аутентификация: Client Credentials (OAuth 2.0). Ограниченный набор разрешений: только те endpoint'ы и операции, которые нужны конкретному клиенту (например, приём webhook платёжного провайдера — только POST на /api/v1/webhooks/payments). Не привязана к «своим» данным пользователя; доступ задаётся client_id и scope в IAM.

| SUPPORT
| Поддержка
| Расширение
| Чтение профилей пользователей и их запросов/уведомлений (в рамках тикетов поддержки); READ на users (ограниченные поля), user_requests, notifications; без доступа к платежам и смене ролей. Контекст: тикет или явное согласие.

| AUDITOR
| Аудитор
| Расширение
| Только чтение логов аудита и событий безопасности (audit_logs, security_events); экспорт отчётов для соответствия; READ на audit; без изменения данных; маскирование PII в экспорте по политике.

| BILLING
| Финансовый специалист
| Расширение
| Чтение платёжных транзакций, истории, отчётов; READ на payments; без изменения платежей и без полных профилей пользователей (идентификаторы и агрегаты по необходимости).
|===

*Разрешения (Permissions):* READ (чтение), WRITE (создание, изменение), DELETE (удаление), EXECUTE (выполнение операции, например «отправить запрос», «инициировать платёж»), MANAGE (управление чужими ресурсами — назначение ролей, отмена чужих запросов и т.п.). Маппинг «роль → разрешения по типу ресурса» хранится в конфигурации API Gateway и/или в User Service (таблица `user_permissions` для переопределений на уровне пользователя); при запросе проверяется наличие нужного разрешения у одной из ролей пользователя и при необходимости владелец ресурса.

===== Процесс добавления и изменения ролей

*Кто может назначать и снимать роли:*

  * Назначение и снятие ролей пользователям выполняют только пользователи с ролью *ADMIN* (Администратор). В Keycloak это реализуется через realm roles и ограничение доступа к админ-консоли или через отдельный API User Service (например, `PUT /api/v1/admin/users/{id}/roles`), защищённый проверкой роли ADMIN в JWT.

*Где хранятся роли:*

  * *IAM (Keycloak):* роли realm/клиента; при логине роли попадают в JWT (claim `realm_access.roles` или `resource_access.<client>.roles`). Это источник истины для аутентификации и первичной проверки на API Gateway.
  * *User Service (users_db):* таблица `user_roles` (user_id, role_name, granted_at, granted_by, expires_at) — зеркало или расширение для синхронизации с IAM, учёта срока действия роли и аудита «кто кого назначил». Синхронизация: при логине или по событию из IAM User Service обновляет user_roles; при назначении роли через User Service — вызов Keycloak Admin API и запись в user_roles.

*Процесс добавления новой роли в систему (редкая операция):*

  1. Изменение политики доступа: описание роли, перечень разрешений по ресурсам, согласование (внутренний процесс/документ).
  2. Keycloak: создание новой realm-роли (или client role) с именем, совпадающим с техническим именем (например, SUPPORT, AUDITOR, BILLING).
  3. API Gateway / User Service: обновление конфигурации маппинга «роль → разрешения» (список endpoint'ов и требуемых разрешений по ролям).
  4. При необходимости — миграция БД (если в user_roles есть ограничение на перечень role_name — добавить новое значение).
  5. Назначение роли пользователям — через админ-интерфейс или API (только ADMIN).

*Процесс изменения ролей у пользователя:*

  1. Администратор вызывает API (например, User Service) или админ-консоль Keycloak.
  2. Проверка: у текущего пользователя есть роль ADMIN.
  3. Изменение: добавление/удаление роли у целевого пользователя в Keycloak и запись в user_roles (granted_by = current user_id, granted_at = now; при снятии — удаление или пометка revoked).
  4. Аудит: событие «роль назначена/снята» (кто, кому, какая роль, когда) в audit_logs; при использовании User Service — публикация в Event Bus для Audit Service.
  5. Вступление в силу: при следующем обновлении токена (или при следующем запросе, если проверка ролей идёт из БД/кэша с инвалидацией) пользователь получает обновлённый набор ролей.

*Срок действия роли (опционально):* поле `expires_at` в `user_roles` позволяет задать временную роль; при проверке прав (в User Service или при синхронизации в JWT) роли с истёкшим expires_at не учитываются. Продление — повторное назначение роли администратором.

===== Автоматизация проверки соответствия политик доступа

*Цель:* убедиться, что конфигурация ролей и проверки прав не расходится с эталонной политикой и что неправомочный доступ отклоняется.

*Регулярные проверки:*

  * *Тесты авторизации (unit / integration):* для каждого критичного endpoint'а и роли — тест «пользователь с ролью X получает 200/201 при разрешённой операции» и «пользователь без нужной роли получает 403». Роли USER/VIEWER — дополнительно тесты «доступ к чужому ресурсу (другой user_id) возвращает 403 или 404». Автоматизация: CI (например, в рамках тестов приложения или отдельного набора тестов политик).
  * *Эталонная конфигурация ролей и маппинга:* описание «роль → разрешения по ресурсу/endpoint» хранится в репозитории (YAML/JSON или код); при деплое конфигурация Keycloak и Gateway сверяется с эталоном или применяется из IaC (Terraform, Ansible, Keycloak Admin API из скрипта). Изменения ролей и прав проходят через code review.
  * *Аудит доступа и ревью:* логирование отказов в доступе (403) и успешных вызовов админ-операций (назначение ролей, изменение пользователей). Периодический разбор (например, ежеквартально) и алерты на аномалии (массовые 403 по одному пользователю, назначение роли ADMIN вне регламента). Связь с 2.09 (Observability) и 3.02 (Аудит безопасности).
  * *Проверка «роль SERVICE»:* для каждого client_id с ролью SERVICE явный перечень разрешённых scope или endpoint'ов; тесты или скрипты проверяют, что сервисный аккаунт не имеет доступа к endpoint'ам, не указанным в перечне.

*Итог:* процесс добавления/изменения ролей централизован у администратора, роли хранятся в IAM и User Service с синхронизацией и аудитом; соответствие политикам обеспечивается тестами, эталонной конфигурацией в репозитории и ревью аудит-логов.

==== Соответствие модели требованиям

[options="header",cols="1,2"]
|===
| Требование (FR-002 / FR-003 / FR-006)
| Отражение в модели

| OAuth 2.0, OIDC, JWT
| IAM (Keycloak), api-gateway → iam (JWT, JWKS), api-gateway → iam_ext (OAuth2, OIDC)

| Выдача токенов
| IAM; клиенты получают токены через Gateway/iam_ext (Authorization Code, refresh)

| Проверка токенов
| API Gateway: валидация JWT по JWKS, проверка прав; без вызова IAM на каждый запрос

| RBAC, роли в JWT
| User Service (роли, permissions), API Gateway проверяет права; полный набор ролей (Администратор, Оператор, Пользователь, Наблюдатель, Сервис, Поддержка, Аудитор, Финансовый специалист) и процессы — раздел «Управление доступами (RBAC)»

| Экспирация и refresh
| Access 15 мин (эталон Keycloak) / допускается 15–30 мин по FR-002; SSO idle 30 мин, *SSO max 24 ч* (`ssoSessionMaxLifespan`); refresh в пределах SSO-сессии; обновление через IAM (Keycloak / iam_ext)

| Управление сессиями
| User Service синхронизация с Keycloak (user-service → iam), кэш сессий (cache)

| Кэш и access token (FR-006)
| TTL 30 мин в FR-006 — не для обхода `exp` access token (15 мин в Keycloak): на Gateway каждый запрос — проверка claims JWT; в Redis — JWKS, профили, blacklist; см. раздел «Кэш и JWT»
|===

*Вывод:* текущая модель (IAM, API Gateway, User Service, связи с iam_ext и cache) удовлетворяет требованиям аутентификации и авторизации. В конфигурации Keycloak зафиксированы: TTL access token (15 мин в JSON), PKCE для SPA, JWKS, rotation refresh, `ssoSessionIdleTimeout` 30 мин, *`ssoSessionMaxLifespan` 24 ч* — согласовать с FR-002 (см. актуализацию в 1.01). Готовая конфигурация — `keycloak/realm-system-design.json`, импорт через Admin UI или `keycloak/apply-realm.sh`; см. `keycloak/README.md`.
