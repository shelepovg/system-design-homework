=== Планы тестирования

Ниже — план проверок, согласованный с текущими артефактами репозитория (GitLab CI, GitHub Actions, `openapi/`, модель в LikeC4) и с нефункциональными требованиями по нагрузке и наблюдаемости (NFR-002, NFR-003, NFR-009; док. *1.02*, *2.09*).

==== Уже автоматизировано в репозитории

[options="header",cols="2,3"]
|===
| Контур | Что выполняется

| *GitHub Actions* (`.github/workflows/test.yml`, ветки `feature/*`)
| `npm install`, `npm run test:likec4` — проверки консистентности модели LikeC4 (контейнеры, хранилища, связи) через Vitest, без сборки диаграмм.

| *GitLab CI* (`infra/gitlab/.gitlab-ci.yml`, стадия *build*, job `validate:kustomize`)
| На каждом прогоне: `kubectl kustomize infra/k8s` — проверка, что Kustomize-набор манифестов собирается без ошибок (без подключения к кластеру).

| *GitLab CI* (стадии *build* / *test*, job'ы `build:docker`, `test:integration`)
| Выполняются *только* если в CI/CD задана переменная *File* `API_GATEWAY_JAR` (готовый JAR gateway, собранный вне репозитория). Тогда: сборка образа по `infra/docker/services/api-gateway/Dockerfile`, push в Registry, pull и запуск контейнера, проверка `GET /actuator/health` и `status":"UP"`. Это интеграционная проверка «образ поднимается и отвечает health», не сценарии API.
|===

Сборка статики LikeC4 для Pages (`.github/workflows/pages.yml`) к тестам приложения не относится и в планах ниже не дублируется.

==== Уровни тестирования (целевое состояние при полной реализации сервисов)

===== Модульные и компонентные тесты

* *Backend (Spring Boot):* JUnit 5, Mockito/WebMvcTest/Slice-тесты для сервисов, репозиториев (с Testcontainers для PostgreSQL/Redis при необходимости), валидации DTO.
* *API Gateway:* тесты маршрутизации, фильтров безопасности, интеграция с тестовым issuer JWT (WireMock или Testcontainers Keycloak).
* *Критерий:* покрытие критичной бизнес-логики и ветвлений; порог покрытия задаётся командой (ориентир не ниже 70–80 % для нового кода в доменных модулях).

===== Контрактные и API-тесты

* Спецификация OpenAPI 3 (`openapi/api-gateway.yaml`) — источник для контрактных тестов (Consumer-Driven Contracts или проверка ответов против схемы).
* Проверка соответствия реализации эндпоинтов `/api/v1/users`, `/api/v1/requests`, `/api/v1/payments`, `/api/v1/notifications` документу *2.12 Форматы взаимодействия* и модели данных (*2.06*).

===== Интеграционные тесты (расширение относительно текущего GitLab job)

* Запуск сервисов с реальными (тестовыми) PostgreSQL, Redis, Kafka (Testcontainers или выделенный стенд).
* Сценарии: создание пользователя, постановка запроса в очередь, инициация платежа (мок провайдера), публикация/потребление событий для Notification и Audit.
* Проверка интеграции с Keycloak (получение токена, проверка ролей в claims согласно *3.01*).

===== Сквозные (E2E) тесты

* Через публичную точку входа (Ingress / API Gateway): сценарии «клиент → gateway → микросервисы» с реальным или стейджинговым IAM.
* Минимальный набор smoke после каждого деплоя на staging; расширенный регресс перед промоутом в production.

===== Нагрузочное и стресс-тестирование

* Обоснование целевых RPS и запаса — *2.07 Расчеты показателей решения*, *4.01* (пик 200k RPS, средняя 50k RPS, деградация не ниже 20k RPS).
* Инструменты: k6, Gatling или аналог; профили нагрузки на API Gateway и на доминирующий по трафику Request Processing Service.
* Метрики успеха: p95/p99 латентности, доля ошибок, устойчивость при плановом масштабировании (HPA); результаты фиксируются для уточнения сайзинга (*4.01*, блок «Сайзинг»).

===== Наблюдаемость и тесты готовности к эксплуатации

* Наличие и корректность метрик Prometheus (`/actuator/prometheus`), трассировок (OpenTelemetry), алертов по *2.09* и *2.10*.
* Проверка liveness/readiness в Kubernetes (в манифестах `infra/k8s` уже заданы пробы к `/actuator/health` для Java-сервисов после появления реальных образов).

==== Связь с CI/CD

* *Merge request / feature:* Vitest на GitHub (если настроен workflow); в GitLab на каждом коммите выполняется как минимум `validate:kustomize`.
* *Ветка `main`:* ручной `deploy:kubernetes` после успешного `validate:kustomize`. Обновление образа `api-gateway` в кластере из пайплайна выполняется только при успешных `build:docker` и `test:integration` в том же прогоне (задана переменная `API_GATEWAY_JAR`).
* Когда в репозитории появится сборка JAR (Maven/Gradle job), вместо ручной подачи файла можно передавать артефакт между job'ами; модульные и API-тесты Java добавляют до или после `build:docker` по политике команды.
* *Отчёт о результатах в Telegram* (MVP, см. *4.02*): при падении любого job и при успешном деплое на `main` — не дублирует успешные промежуточные этапы, чтобы не перегружать канал до появления полноценного контура уведомлений и алертинга.
