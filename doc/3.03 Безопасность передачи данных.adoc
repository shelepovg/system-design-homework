=== Безопасность передачи данных

Определения данных, подлежащих дополнительному шифрованию поверх защищённого канала. Исходные требования: NFR-005 (Безопасность), критерии «в движении: TLS 1.3», «в покое: AES-256», управление ключами через KMS.

==== Использование SSL/TLS для защиты данных в сети

*Текущее отражение в проекте:*

* Модель (likec4): клиенты (web, android, ios) подключаются к load-balancer по HTTPS; в описании связи указано «HTTPS, TLS 1.3; HTTP/1.1, HTTP/2». Load-balancer выполняет TLS termination (summary: «распределение трафика, TLS termination»).
* Документ 2.11: протокол клиент → LB — HTTPS (TLS 1.3), порт 443; порт 80 — редирект на 443. Внутри периметра (API Gateway → Backend) — HTTP/1.1 или HTTP/2, TLS опционально.
* NFR-005: «В движении: TLS 1.3 для всех сетевых соединений».

*Рекомендуемые настройки и принципы:*

* *Версия протокола:* только TLS 1.2 и TLS 1.3; TLS 1.0/1.1 отключены. На edge (Nginx/load-balancer) явно задать `ssl_protocols TLSv1.2 TLSv1.3;`.
* *Perfect Forward Secrecy (PFS):* использовать только наборы шифров с ephemeral key exchange (DHE или ECDHE), чтобы компрометация долгосрочного ключа сервера не позволяла расшифровать ранее перехваченный трафик. Рекомендуемые наборы: например `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`, `TLS_AES_128_GCM_SHA256` (TLS 1.3); для TLS 1.2 — ECDHE-RSA-AES256-GCM-SHA384, ECDHE-RSA-CHACHA20-POLY1305 и аналоги. Отключить статические RSA key exchange.
* *HSTS (HTTP Strict Transport Security):* включить на edge (load-balancer / front), чтобы браузеры не обращались по HTTP к домену. Заголовок: `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`. Редирект 80 → 443 сохранить как fallback для первого захода; после первого ответа с HSTS браузер будет использовать только HTTPS.
* *Сертификаты:* сертификаты от доверенного CA (публичного или корпоративного); срок жизни не более 13 месяцев; автоматическое продление (например, ACME/Let's Encrypt или корпоративный PKI). Нагрузка на load-balancer — один или несколько сертификатов для публичных имён (API, веб-интерфейс).
* *Внутренний трафик (LB → Front, LB → API Gateway, API Gateway → Backend):* внутри доверенного периметра TLS опционально по политике (2.11). Для соответствия формулировке NFR-005 «TLS 1.3 для всех сетевых соединений» рекомендуется либо: (a) включить TLS 1.3 и на внутренних каналах (mTLS или односторонний TLS), либо (b) явно зафиксировать в политике, что «все соединения» означают все соединения с ненадёжных сетей (клиент–LB, Gateway–IAM, сервисы–внешние системы); внутренняя сеть считается доверенной при наличии сегментации и контроля доступа. Для платежей и персональных данных предпочтительно (a).
* *Внешние системы:* вызовы к IAM (api-gateway → iam, iam_ext), платёжная система, уведомления — только по HTTPS (TLS 1.2+), проверка сертификата сервера, без отключения верификации.

*Принципы работы (кратко):*

* TLS обеспечивает конфиденциальность и целостность данных в канале; аутентификацию сервера — через сертификат.
* HSTS устраняет downgrade на HTTP и снижает риск MITM при первом подключении после включения preload.
* PFS ограничивает последствия утечки приватного ключа сервера во времени (нельзя расшифровать старые сессии).
* Ротация сертификатов и отказ от устаревших протоколов/шифров — часть регулярной гигиены (согласуется с NFR-005, ротация ключей через KMS).

==== Какие данные шифровать дополнительно (поверх защищённого канала)

Даже при использовании TLS часть данных имеет повышенную ценность или длительный срок жизни: при утечке логов, бэкапов или кэша злоумышленник не должен получить их в открытом виде. Ниже — категории данных и необходимость дополнительного шифрования.

*Рекомендуется шифровать дополнительно (алгоритм — см. ниже):*

* *Учётные данные и секреты:* пароли (хэши уже хранятся в IAM; при синхронизации не передавать пароли в открытом виде), client_secret, refresh_token при хранении в БД или логах — не логировать; при хранении в БД (если потребуется) — шифрование полей (AES-256-GCM) с ключами из KMS.
* *Платёжные реквизиты:* полные номера карт не хранить (PCI DSS); токены платёжного провайдера, ссылки на платёжные сессии — при хранении в БД шифровать чувствительные поля (AES-256-GCM). В движении — только по HTTPS; дополнительное шифрование на уровне приложения для платёжных payload не обязательно при гарантированном TLS 1.3 и отсутствии логирования тел запросов с картами.
* *Персональные данные (PII) высокой чувствительности:* паспортные данные, полные номера документов, биометрия — при хранении в БД (если понадобится) — шифрование на уровне полей (AES-256-GCM), ключи в KMS. В движении достаточно TLS; в логах — только маскирование или исключение.
* *Данные в бэкапах и объектном хранилище:* бэкапы БД и WAL (2.13) — шифрование в покое (AES-256), что уже задано в NFR-005; снимки Redis при выгрузке в объектное хранилище — аналогично шифрование в покое. Канал до хранилища — HTTPS (S3/MinIO).
* *Кэш (Redis):* сессии, профили, результаты запросов могут содержать PII. Рекомендация: либо шифрование чувствительных значений в Redis (AES-256-GCM, ключ из KMS), либо строгое ограничение доступа к Redis и отсутствие в кэше полных платёжных/PII без шифрования; для соответствия «все данные зашифрованы в покое» (NFR-005) предпочтительно encryption at rest на уровне Redis (например, Redis Enterprise или прозрачное шифрование тома) и/или шифрование чувствительных полей приложением.

*Не требуется дополнительное шифрование поверх TLS для:*

* Обычных запросов/ответов API (JSON с неплатёжными, не-PII данными) при гарантированном TLS 1.3 на всём пути.
* JWT в заголовке Authorization — передаются только по HTTPS; содержимое JWT не секретное (подпись обеспечивает целостность и аутентичность). Секретным является только сам канал.

==== Выбор алгоритма шифрования

*В движении:* TLS 1.3 с наборами шифров по умолчанию (AES-GCM, ChaCha20-Poly1305) — достаточен; отдельный алгоритм на уровне приложения для трафика не вводится.

*В покое и для дополнительного (field-level) шифрования:*

* *Стандарт:* AES-256 в режиме GCM (AES-256-GCM), как указано в NFR-005. GCM даёт конфиденциальность и аутентичность (AEAD); IV/nonce — уникальные для каждого шифрования (например, 96 бит random), не переиспользовать с одним ключом.
* *Управление ключами:* KMS (Key Management Service) — генерация и хранение мастер-ключей; приложение получает DEK (Data Encryption Key) или выполняет шифрование в KMS; для больших объёмов — envelope encryption: KMS шифрует DEK, DEK шифрует данные. Ротация ключей каждые 90 дней (NFR-005) — ротация мастер-ключей в KMS; перешифрование данных — по политике (постепенно при доступе или плановыми задачами).
* *Хэширование паролей (IAM):* не «шифрование», но для полноты — стойкое хэширование (bcrypt, scrypt или Argon2) с salt; хранение в Keycloak по умолчанию соответствует лучшим практикам.

==== Перечень данных для field-level шифрования и маскирования в логах

Перечень зафиксирован для реализации дополнительного (field-level) шифрования в БД/кэше и обязательного маскирования в логах (FR-004, 2.09). Алгоритм шифрования полей — AES-256-GCM, ключи из KMS (см. выше и 2.13).

*Field-level шифрование (при хранении в БД или в кэше):*

[options="header",cols="1,2,2"]
|===
| Категория данных
| Примеры полей / типов данных
| Действие

| Учётные данные и секреты
| client_secret, refresh_token (если хранятся в БД), API-ключи внешних систем
| Шифрование поля (AES-256-GCM). Не логировать в открытом виде.

| Платёжные реквизиты и токены
| Токен платёжного провайдера, ссылка на платёжную сессию, idempotency_key (при необходимости)
| Шифрование чувствительных полей. Полные номера карт не хранить (PCI DSS).

| PII высокой чувствительности
| Паспортные данные, полные номера документов, биометрия (если появятся в модели)
| Шифрование полей при хранении в БД; в логах — маскирование или исключение.

| Сессии и токены в кэше
| Значения сессий, refresh_token в кэше (если применимо)
| Encryption at rest Redis (2.13); при необходимости — шифрование значения приложением.
|===

*Маскирование в логах (обязательно):*

  * *Не логировать в открытом виде:* пароли, client_secret, refresh_token, access_token (JWT целиком или тело), полные номера карт, CVV.
  * *Маскировать (оставлять только часть или хэш):* email (например, u***@example.com), телефон (последние цифры скрыты), номер документа (только последние 4 символа), user_id — по политике (можно оставить для трассировки, если не считается PII в логах).
  * *Стандартные поля запросов:* заголовок Authorization — не логировать или заменять на «REDACTED»; тело запроса с платёжными данными — не логировать или логировать только метаданные (transaction_id, сумма без привязки к карте).
  * Реализация: на этапе обработки логов (Vector или аналог) — правила маскирования по полям и паттернам; в коде приложения — не передавать чувствительные поля в структурированные логи (2.09, FR-004).

*Вывод:* проект удовлетворяет требованиям безопасности передачи данных. В документе 2.11 зафиксированы настройки HSTS и PFS на edge и граница доверенной сети; в документе 2.13 — применение AES-256 (AES-256-GCM) в покое для PostgreSQL, Redis и бэкапов и использование KMS; в данном документе (3.03) определён перечень полей и категорий данных для field-level шифрования и маскирования в логах.
